# Pitfalls & fixes — read this before debugging from scratch

This is a running log of real problems hit while moving this site off
Lovable and self-hosting it, in the order they happened. If something
breaks and it *feels* familiar, check here first — there's a decent
chance it's already been solved once and just needs re-applying (e.g.
after a fresh clone, or because a new person is added as admin).

Each entry: **Symptom → Why it happened → How it was fixed → How to
avoid it next time.**

---

## 1. Sign-in button spins forever, never finishes

**Why:** the code called `supabase.auth.signInWithOAuth(...)` without a
`try/catch`. If that call throws (network issue, misconfiguration,
anything), the button's "loading" state never gets turned back off,
and no error message shows either — it just spins silently forever.

**Fix:** wrapped the call in `try/catch` in `src/routes/login.tsx` so
any thrown error resets the button and shows a message instead of
hanging.

**Avoid it:** any `async` click handler that flips a loading state
needs a `try/catch`/`finally` around it, full stop — especially around
calls to Supabase, since its client throws on network errors rather
than always returning `{ error }`.

## 2. Console error: `ReferenceError: lovable is not defined`

**Why:** the site was deployed as a Cloudflare Worker, but there's
**no CI/CD** — no GitHub Action, no Cloudflare Git integration. Pushing
to GitHub does nothing to the live site by itself. Someone has to
manually run the build + deploy. This error showed up because the
*live* Worker was running a build from *before* the Lovable OAuth code
was removed, even though GitHub had the fix.

**Fix:** manually rebuilt and redeployed:
```powershell
git pull origin main
npm install
npm run build
npx wrangler deploy --config .output/server/wrangler.json
```

**Avoid it:** **after every push to `main`, redeploy using the four
commands above.** This is the single most common way to see "old
behavior" after a fix was supposedly made — the code was right, it
just wasn't live yet. Setting up a GitHub Action to do this
automatically is still an open task (see `EDITING-CONTENT.md` /
ask for it directly).

## 3. Local `git commit` shows files "modified" that you didn't touch

**Symptom:** `.env`, `package-lock.json`, `src/routeTree.gen.ts` show
as modified even though you didn't edit them.

**Why:** `routeTree.gen.ts` is auto-regenerated by TanStack Router
every time you run `npm run dev` or `npm run build`. `package-lock.json`
can shift slightly between npm versions/platforms. `.env` can show
diffs if it was edited on a different machine/session.

**Fix:** before committing, check what actually changed:
```powershell
git diff -- .env src/routes/login.tsx    # or whichever files matter
git checkout -- package-lock.json src/routeTree.gen.ts   # safe to discard
```
Only worry about files with real, intentional content differences.

**Avoid it:** don't blindly `git add -A && git commit` when you see
unexpected files — diff first, especially `.env`.

## 4. The "real" Supabase project wasn't visible in the connected account

**Symptom:** the site's `.env` pointed at a Supabase project
(`eikjjvpujcsanoxyfxxn`) that didn't show up when connecting a
personal/organization Supabase account.

**Why:** Lovable Cloud auto-provisions a Supabase project on its own
managed infrastructure when you build with Lovable. It's not
automatically transferred into your own personal Supabase
organization — that's expected, not a mistake anyone made.

**Fix:** since starting fresh was acceptable, rebuilt the full schema
(all tables, RLS policies, triggers) on a Supabase project actually
owned by this account (`dlinteriors`, ref `ppypgqmcqfoyxiqlaroy`),
using the migration files already checked into `supabase/migrations/`
plus the Drizzle migration for `admin_access_requests`. Then pointed
`.env` and `supabase/config.toml` at the new project and regenerated
`src/integrations/supabase/types.ts`.

**Avoid it:** if you ever see auth/database behavior that doesn't
match what you expect, the first thing to check is **which Supabase
project `.env` actually points to**, and whether that's the project
you think you're looking at in the dashboard.

## 5. Google sign-in "worked" but landed on a broken Supabase URL

**Symptom:** after picking Google, the browser ended up at
`https://<project-ref>.supabase.co/#access_token=...` and showed
`{"error":"requested path is invalid"}`.

**Why:** Supabase Auth only redirects back to a URL that's on its
**Redirect URLs allow-list** (Authentication → URL Configuration). If
the app's real address isn't on that list, Supabase falls back to
sending the session to its own default **Site URL** instead — which,
on a fresh project, is the project's own `*.supabase.co` address. That
address isn't a real page, hence the 404.

**Fix:** in Supabase Dashboard → Authentication → URL Configuration,
set:
- **Site URL** = the real production URL of the site
- **Redirect URLs** includes `<production URL>/login`

**Avoid it:** any time the production domain changes (custom domain
added, moved hosts, etc.), update both of these in Supabase or OAuth
sign-in will break the same way.

## 6. A full OAuth callback URL was pasted into chat — treat as compromised

**What happened:** a browser URL containing `access_token`,
`refresh_token`, and `provider_token` (a live Google API token) was
pasted for debugging. Those aren't diagnostic info — they're active
credentials, equivalent to a password.

**Fix at the time:** the leaked session was deleted directly from
`auth.sessions` in the database (kills the refresh token immediately;
the short-lived access token expired on its own within the hour). The
Google-side token can't be revoked from the database — that needs
manually revoking the app under Google Account → Security →
Third-party access.

**Avoid it:** never paste a full URL that contains
`access_token=`, `refresh_token=`, or `provider_token=` anywhere. If
you need to show a URL for debugging, delete everything after the
`#` or `?` first. If you're checking *which request* failed, the
request's path/host is what matters, not its full query string or
fragment.

## 7. Apple sign-in: "Access Unavailable" in Apple Developer

**Why:** creating a Services ID / Sign-in-with-Apple key requires an
**enrolled, paid ($99/year) Apple Developer Program membership**. A
free Apple ID can sign in to the developer site but can't access
Certificates/Identifiers/Profiles at all.

**Fix (chosen for now):** hid the "Continue with Apple" button in
`src/routes/login.tsx` (commented out, not deleted — the function
that handles it, `socialSignIn("apple")`, was left untouched). Google
sign-in works and is unaffected.

**Avoid it / next steps:** once enrolled in the Apple Developer
Program, follow the steps that were written out in this project's
chat history (Identifiers → Services ID → enable Sign in with Apple →
Keys → download the `.p8` file), then use the
`generate-apple-client-secret.js` script to turn that key into the
JWT Supabase needs, and un-comment the button.

## 8. Admin access: made automatic for specific emails

**What was built:** rather than hardcoding admin emails in the app
(which would need a code change + redeploy every time), an
`admin_email_allowlist` table plus an `AFTER INSERT` trigger on
`auth.users` grants the `admin` role automatically the moment a
matching email signs up (or immediately, for anyone who already has
an account).

**To add another admin later**, run in the Supabase SQL editor:
```sql
insert into public.admin_email_allowlist (email) values ('newemail@example.com');
```
If that person already has an account, also run:
```sql
insert into public.user_roles (user_id, role)
select u.id, 'admin'::app_role
from auth.users u
join public.admin_email_allowlist a on a.email = lower(u.email)
on conflict (user_id, role) do nothing;
```

**Avoid it:** don't hand-edit `user_roles` directly for this purpose —
use the allowlist table so it's consistent and self-documenting.

## 9. Portfolio project pages 404'd even after adding a project in /admin

**Why:** `src/routes/portfolio.tsx` (the grid) tried Supabase and fell
back to a hardcoded sample list in `src/lib/projects.ts` if the
database was empty — but `src/routes/portfolio.$slug.tsx` (each
project's own page) **never checked the database at all**. It only
ever read the hardcoded sample list. So a real project added via
`/admin` would show up in the grid... and 404 the moment you clicked
into it.

**Fix:** the `$slug` page's loader now checks the database first
(project row + its gallery images + other published projects for
"related"), and only falls back to the hardcoded sample data if
nothing matching is found in the database.

**Avoid it:** when a page has a "list" and a "detail" view, both need
to be wired to the same real data source — checking only one is a
classic way to end up with a feature that half-works.

## 10. `/admin` → Services had zero effect on the live Services page

**Why:** the same kind of gap as #9, but worse: `src/routes/services.tsx`
didn't query Supabase **at all** — it only read hardcoded default
copy from `src/lib/site-content.ts`. The `AdminServices.tsx` panel was
fully wired to write to the real `services` database table, but
nothing on the public site ever read from it.

**Fix:** `services.tsx` now checks the `services` table for published
rows first, and only uses the hardcoded placeholder cards if none
exist yet.

**Avoid it:** if an admin panel lets you edit something, actually open
the corresponding public page's source and confirm it reads from the
same table — don't assume it does just because the admin form saves
successfully.

## 11. Phone number shown twice, only one was editable

**Why:** the homepage hero and bottom CTA read a phone number from
`site_content` (`home.hero.phoneTel` / `home.contactCta.phoneTel`),
while the footer and Contact page read a *different* phone number
from the `contact_info` table. Two sources of truth, two different
placeholder values, easy to update one and forget the other.

**Fix:** removed the phone fields from `site_content` entirely.
Homepage hero and CTA now use the same `useContactInfo()` hook the
footer already used. There's exactly one place to edit it now:
`/admin` → Contact.

**Avoid it:** if you ever see the "same" piece of information (phone,
email, a date, a price) hardcoded or fetched in more than one place in
the code, that's a sign it should be pulled from one shared source
instead — otherwise they will eventually disagree.

## 12. Contact info shown on the live site may not be real

**What happened:** when the database had to be rebuilt from scratch
(see #4), the `contact_info` table was seeded with placeholder values
(`hello@dlinteriors.co.za`, `+27 11 000 0000`, `Johannesburg, South
Africa`) copied from the app's own fallback defaults — not the real
business's actual contact details, which weren't recoverable from the
old, unreachable Supabase project.

**Status:** unresolved as of this writing. **Go to `/admin` → Contact
and enter the real phone number, email, and address before treating
the site as ready for the public.**

**Avoid it:** whenever a database is rebuilt or migrated, confirm
every piece of contact/business information against the real source
(the business owner) rather than trusting a rebuilt default value.
